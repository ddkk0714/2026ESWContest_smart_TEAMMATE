# DESKMATE 앱 연결 안정화 개발 계획

> 작성 2026-09-29 · 대상 `display/atlas/ui_env_app` (Pi 5 Atlas Flutter 앱) · 기준 코드 PR #27 (`feat/display-hub-followup`)

## 1. 목표와 배경

부스·교내 LAN·휴대폰 핫스팟 등 어떤 망에서 켜도 앱이 스스로 연결 문제를 찾고, 사람 손을 최소로 해서 복구되게 한다.
결선 시연 환경이 매번 달라 연결 실패가 가장 큰 현장 리스크이기 때문이다.

대상은 세 가지다.

- **통신 상태 점검과 빠른 리로드** — MQTT·hub·센서·카메라·블루투스 연결을 한곳에서 보고, 앱 재시작 없이 다시 연결한다.
- **앱 실행 시 MQTT 예외 처리와 연결 가이드** — 브로커에 못 붙어도 앱은 뜨고, 원인과 조치를 안내한다.
- **블루투스 연결 매끄럽게** — 스피커·램프를 매번 다시 검색·선택하지 않는다.

## 2. 결정 사항 (2026-09-29 합의)

| 항목 | 결정 |
| --- | --- |
| MQTT 브로커 주소 | 앱에서 변경하고 보드 파일에 저장. 우선순위: 저장된 주소 → 빌드에 넣은 주소(`DESKMATE_MQTT_HOST`) → 연결 가이드 |
| 연결 상태 UI | 별도 **'연결' 탭** 신설. 문제가 있을 때만 **경고 배지**가 뜨고, 누르면 연결 탭으로 이동. **상단 상태 줄은 누르면 사라지고**, 새 문제가 생기면 다시 뜬다 |
| 블루투스 | 마지막으로 연결에 성공한 스피커·램프에 앱 실행 때 **자동 재연결** |
| 카메라(자세) | **연결 복구만** 범위에 포함(재탐색·리로드·권한 확인). 카메라 기능 자체는 늘리지 않아 I7(카메라 사용 여부) 결정과 무관 |

공통 원칙: 연결 실패는 어떤 경우에도 앱 실행이나 FSM 판정을 막지 않는다. 블루투스·카메라는 선택적 출력이라 실패해도 화면은 계속 돈다.

## 3. 현재 코드의 문제점

가장 큰 문제는 MQTT 주소가 빌드 때 고정돼 있고, 실패 원인을 구분해 알려 주지 못한다는 점이다.

| 영역 | 문제 | 근거 |
| --- | --- | --- |
| MQTT | 브로커 주소가 빌드 시 고정. Pi 4 IP가 바뀌면 재빌드·재설치 필요. 앱 안 주소 변경은 HTTP 개발 경로에만 있음 | `main.dart` `_mqttHost`, `_connectHub` |
| MQTT | 주소가 틀리거나 브로커가 꺼져 있으면 "MQTT 재연결 중"만 표시. 네트워크·브로커·hub 중 어디 문제인지 구분 없음 | `state_source.dart` `connectionLabel` |
| MQTT | `autoReconnect` 에만 의존. 연결은 됐는데 메시지가 안 오는 상태를 스스로 복구 못 함(15초 무수신 판정은 배지에만 사용) | `main.dart` `_linkStaleAfter` |
| MQTT | `deskmate/health/#`(hub·ESP32·collector online/offline) 미구독 → hub가 죽었는지 모름 | `state_source.dart` 구독 목록 |
| 카메라 | camsvc → 보드 직결(UART) → 데모 탐색이 앱 시작 때 1회뿐. camsvc가 늦게 뜨면 데모에 머묾 | `posture_screen.dart` `_startBestLocalSource` |
| 카메라 | 보드 직결에 필요한 `privileged.peripheral` 권한이 통합 앱에 없음(실기 확인 필요) | `atlas/meta/appinfo.json`, `docs/posture-camera.md` |
| 블루투스 | 실행할 때마다 검색(8초 고정) → 스피커 선택 → 램프 선택 반복. 선택 기기를 기억하지 않음 | `bluetooth_service.dart` `scan`, `bluetooth_control_page.dart` |
| 블루투스 | 램프 GATT 연결을 캐시한 뒤 끊겨도 버리지 않음 → 한 번 끊기면 앱 재시작 전까지 조명이 안 바뀜. 오류는 조용히 무시 | `feedback_policy.dart` `IlinkLampFeedback._connection` |
| 블루투스 | 권한 동의 후 "다시 검색을 누르세요"로 끝나 한 번 더 눌러야 함 | `bluetooth_service.dart` `ensureBluetoothPermission` |

## 4. 단계별 개발 계획

| 단계 | 내용 | 산출물 | 기간 |
| --- | --- | --- | --- |
| 0. 기반 | 연결 대상별 상태 모델과 설정 저장소 | `LinkStatus`(상태: 정상/지연/끊김/미설정, 마지막 수신 시각, 원인 코드, 권장 조치) · `SettingsStore`(camtest `HubStore` 일반화: MQTT·카메라 주소, 블루투스 기기를 보드 파일에 저장) | 0.5일 |
| 1. MQTT 시작 점검 | 앱 실행 시 4단계 진단(§5)과 원인별 안내. 기존 IP 키패드(`showHubSetup`) 재사용해 주소 입력. 앱은 막지 않고 "다시 시도 / 주소 변경 / 데모로 계속" 제공 | 진단기 + 가이드 시트 + 주소 저장 | 1일 |
| 2. 연결 탭과 리로드 | 연결 탭(MQTT·hub·ESP32 센서·키스트로크·카메라·스피커·램프), 경고 배지 → 연결 탭 이동, 상태 줄 탭하면 닫힘. 대상별 "다시 연결"과 "전체 리로드"(앱 재시작 없이 연결 객체 재생성 + 카메라 재탐색) | 연결 탭 + 자동 복구 규칙 | 1~1.5일 |
| 3. 블루투스 | 저장 기기에 검색 없이 자동 재연결, 램프 GATT 캐시 오류 시 폐기·1회 재시도, KLZS-L1 스피커+램프 이름으로 짝지어 한 번에 연결, 검색 결과 나오는 대로 추가, 권한 동의 후 자동 진행 | 블루투스 서비스·페이지 개선 | 1일 |

자동 복구 규칙 (2단계):

- MQTT가 연결 상태인데 15초 넘게 메시지가 없으면 강제로 다시 연결한다. 실패가 이어지면 재시도 간격을 늘린다(백오프).
- 카메라가 데모 상태이면 30초마다 camsvc → 보드 직결 순으로 다시 탐색한다.
- 센서 신선도는 `state/phase` 의 `sensor_summary` 와 `deskmate/health/<node>` 로 판정한다.

## 5. MQTT 시작 점검 — 진단 단계와 안내

| 단계 | 판정 | 실패 시 안내 |
| --- | --- | --- |
| ① 네트워크 도달 | 브로커 주소의 TCP 1883에 2초 안에 연결 | Pi 4 전원·케이블·같은 망인지 확인. IP가 바뀌었으면 주소 다시 입력 |
| ② 브로커 응답 | MQTT CONNACK 수신 | 브로커 미기동 → Pi 4에서 `sh /data/share/deskmate/bin/pi4-broker-start.sh` |
| ③ hub 생존 | `deskmate/health/hub` = online | hub 미기동 → `hub/atlas/tools/pi4-hub-activate.sh` |
| ④ 상태 수신 | 첫 `deskmate/state/phase` 를 10초 안에 수신 | hub는 떴는데 FSM 출력 없음 → 센서 연결·hub 로그 확인 |

어느 단계에서 실패해도 앱은 계속 뜬다. 가이드 시트의 선택지는 "다시 시도 / 주소 변경 / 데모로 계속" 세 가지다.

## 6. 검증 방법

- **단위 테스트:** 가짜 연결 객체(MQTT·camsvc·블루투스)로 진단 단계, 자동 복구, 설정 저장을 테스트한다. 이 PC에는 flutter가 없어 **Atlas Docker 환경에서 실행**한다.
- **실기 체크리스트:**
  - [ ] 브로커를 끈 채 앱 실행 → ② 안내, 브로커 켜면 자동 복구
  - [ ] hub를 끈 채 실행 → ③ 안내
  - [ ] Pi 4 IP 변경 → 앱에서 주소 입력 후 재빌드 없이 연결, 재부팅 후에도 유지
  - [ ] 랜선 분리 후 재연결 → 15초 안에 경고 배지, 복구 후 사라짐
  - [ ] camsvc를 앱보다 늦게 기동 → 30초 안에 자세 화면 전환
  - [ ] 스피커 전원 껐다 켜기 → 자동 재연결, 램프 끊김 후 다음 phase 전환 때 복구
  - [ ] 앱 재실행 → 스피커·램프 검색 없이 연결

## 7. 일정·의존성·리스크

- **시작 시점:** `main.dart`·`posture_screen.dart` 가 PR #27과 겹치므로 **PR #27 머지 후 main에서 시작**한다. 머지가 늦어지면 PR #27 브랜치 위에 이어서 쌓는다.
- **목표:** 통합 MVP(10-05) 전에 0~2단계 완료, 3단계는 그다음.
- **리스크**
  - Flutter 테스트를 이 PC에서 못 돌림 → Atlas Docker 빌드 환경 확보가 선행 조건.
  - Atlas Bluetooth1 D-Bus API에 "페어링된 기기 목록"이 있는지 미확인 → 없으면 저장된 주소로 A2DP 연결을 바로 시도.
  - `privileged.peripheral` 권한 추가가 Atlas 정책상 허용되는지 실기 확인 필요.
  - 카메라 관련 작업은 I7 결정에 따라 시연 빌드에서 빠질 수 있다(연결 복구 코드는 무해).
